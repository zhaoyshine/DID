# 用户偏好

## 开发工作流

- 好的开发工作流：调研 → 用户确认改动方案 → 按方案开发 → 对改动文件跑测试、跑 lint → 按项目要求创建 PR
- 用 git 管理的项目，用 git worktree 并行开发
- 写代码/测试前，先看现有文件怎么写（factory、helper、命名约定），照既有风格写，不自造新约定
- 在关键里程碑设置人工确认检查点（例如方案确认、diff 确认）；检查点不可跳过或合并，未经明确批准不进入下一步
- 只写重要注释；简洁清晰，不复述「是什么」

## 提交与 PR

- 提交格式使用 conventional commits + Co-Authored-By trailer
- 项目约定（分支名 / 提交格式 / PR 模板）运行时从仓库读取，绝不硬编码
- PR 正文必须是仓库自带 PR 模板的严格逐字拷贝，不增加、删除或重排小节，再在骨架内填写；每节都要有实质内容，或明确标注 N/A
- 先做可逆操作（准备 git worktree、本地规范化），再做不可逆操作（push、开 PR、更新 Jira、标记 ready）

## Git 与 Worktree

- 询问用户是否使用 Worktree
- 读代码前，先把仓库更新到最新主分支，确保工作区干净
- 工作区不干净时，不要擅自 stash/reset/clean；保持原样，交还给用户处理
- 只用 git pull --ff-only；禁止非快进合并

## 测试

- 优先把测试代码加进现有测试文件；新建是最后手段；复用现有 factory/helper/mock 基础设施
- 一个测试用例只断言一个维度；按维度分组
- 修 bug 前先写出一个失败的复现（测试或复现用例），这样才能知道何时真正修好
- 测试质量标准：Fast、Independent、Repeatable、Self-validating、Timely（F.I.R.S.T.）

## 调研

- 每个结论都必须注明出处（URL / 文件路径 / Jira key / PR 号 / 日志片段 / 行号）；不许猜
- 穷尽调用链：每个关键符号 ≥2 条搜索命令，疑似跨仓库时 ≥2 个仓库，每个「已穷尽」的说法都要配上 ≥1 条反证
- 深挖到底：遇到的每个 URL / ticket key / 事件 ID / 错误码 / 文件路径 / PR 号都要打开读一遍
- 同一事实出现在多个来源时，取置信度最低的一档（保守原则）
- 关键调研对象，用至少两种不同的方法或关键词变体确认覆盖；一条命令跑完不算完
- 遇到不认识的名字/服务/库/参数，主动查清背景，不要绕过去
- 不确定的事不要猜；拿不到答案就问用户，并留下痕迹避免反复纠结
- 维护一份「常见偷懒借口」清单（例如「应该都有吧」、「没时间了，先交个简化版」）；这类念头冒出来时，停下来对照原则重查
- 套用自动化判断规则前，先查权威数据源核实真实状态；不要仅凭提取出的原始字段下结论

## 规划

- 计划里每一步都是单一动作（2-5 分钟粒度）；不要过度复杂
- 同一模式重复的机械改动合并成一个 task；初始化 / 配置 / 脚手架 / 文档步骤并入需要它们的 task
- 汇总/整合 subagent 输出时，重新归纳提炼；不要原样粘贴，也不要重新评判或改写 subagent 已给出的结论
- 补充说明/注解不得复述已有内容；只写正文没有覆盖的增量信息
- 避开常见的 AI 写作腔：高频填充词（「此外」「值得注意的是」「深入探讨」等）、宣传式夸张、含糊归因、模板化的「挑战与展望」段落、否定式排比、回避系动词、尺度错配的「从 X 到 Y」、滥用破折号 / 加粗 / 表情符号、用行内小标题复述同一观点、协作腔口语痕迹、知识截止声明、谄媚语气、填充短语、过度限定、空洞的积极结论

## 沟通

- 意图 / 模式无法确定时，问用户一个精准的澄清问题，而不是列一串
- 苏格拉底式提问：真有疑问才问，一次只问一个，等答复再问下一个；没有疑问就完全跳过确认

## 文档

- 文档解释「为什么」（意图、理由），不复述步骤已经展示的「是什么」
- 像写文章一样对待文档和提交信息；清晰、精确与内容同等重要
- 把文档当作工作的一部分来建，而不是事后补
