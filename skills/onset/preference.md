# 用户偏好

## 开发工作流

- 看代码时先看现有代码的模块分层、职责边界、文件组织，建立对当前架构的整体认知，再看具体实现
- 好的开发工作流：调研尽可能的收集信息 → 用户确认改动方案 → 按方案开发 → 对改动文件跑测试跑 lint → 按项目要求创建 PR
- 写代码/测试时先读现有文件的写法（factory、helper、命名习惯），照搬其风格，不自造新约定
- 在关键里程碑设置人工确认检查点（例如方案确认、diff 确认）；检查点不可跳过或合并，未经明确批准不进入下一步
- 只写重要注释 why; 注释简洁清晰，直接明了

## Git 与 Worktree 与 PR

- 询问用户是否使用Git Worktree
- 读代码前，先把仓库更新到最新主分支，确保工作区干净
- 提交格式使用 conventional commits + Co-Authored-By trailer
- 项目约定（分支名 / 提交格式 / PR 模板）运行时从仓库读取，绝不硬编码
- PR body 严格逐字复制 repo 自身的 PR template，不新增/删除/重排章节，在骨架内填充内容
- 先做可逆操作（准备 git worktree、本地规范化），再做不可逆操作（push、开 PR、更新 Jira、标记 ready）

## 测试

- 把测试代码加进现有测试文件；最后才考虑新建测试文件；复用现有 factory/helper/mock 基础设施
- e2e 测试优先于单元测试，能写 e2e 测试就不写单元测试
- 一个测试用例只断言一个维度；按维度分组：例如 API响应，DB数据，Redis数据；判断值的内容，而非值是否存在
- 修 bug 前先写出一个失败的复现（测试或复现用例），这样才能知道何时真正修好
- 测试质量标准：Fast、Independent、Repeatable、Self-validating、Timely（F.I.R.S.T.）

## 调研

- 每个结论都必须注明出处（URL / 文件路径 / Jira key / PR 号 / 日志片段 / 行号）
- 穷举调用链；跨 repo 时也要找到对应 repo 的代码，多 Read 目标代码周边 10 行
- 深挖到底：遇到的每个 URL / ticket key / 事件 ID / 错误码 / 文件路径 / PR 号都要打开读一遍
- 同一事实出现在多个来源时，取置信度最低的一档（保守原则）
- 关键调研对象，用至少两种不同的方法或关键词变体确认覆盖
- 遇到不认识的名字/服务/库/参数，主动查清背景
- 不确定的事拿不到答案就问用户，并留下痕迹避免反复纠结
- 套用自动化判断规则前，先查权威数据源核实真实状态；不要仅凭提取出的原始字段下结论

## 注释和文档

- 文档已有说明的内容不写注释，能不写就不写，能写一行就不写两行
- 只写重要的注释，不总结、不转述、不记录变更原因
- 注释简单明了，只写 why（重点、意图、理由），不复述代码的 what
- 写文档要像写 prose 一样用心，清晰、精确与内容同等重要
- 修改时不带历史包袱，被废弃/被取代/已过时的旧方案不再提及，不记录历史变更

## 沟通

- 意图/模式判断不了时，整理问题，一次只问一个，等用户回复再问下一个；无疑点时直接跳过确认
- 苏格拉底式提问：通过连续、有条理的提问，引导对方自主思考、发现真相、厘清概念，而不是直接给答案
